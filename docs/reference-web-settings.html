Backups are not configured

The server holds the only copy of everyone's data. Snapshots run to a versioned bucket with object lock — the only target that survives a compromised server.

Test answers whether the bucket responds, versioning is on, and object lock was enabled at creation. Saving stores the connection on the server and starts hourly snapshots + the retention ladder immediately; SYNCBOX_BACKUP_* env stays as a fallback for headless setup.

Entry & scope. Opens from the sidebar-footer Settings row of the Files UI (reference-web-ui.md); ← All files returns. The rail is server-side state only — everything device-side (sync folder, selective folder tree, Run at login, pause durations, vault auto-lock) lives in the agent Settings window (reference-agent-settings.md) and is deliberately absent here. No sharing settings: share options belong on the share itself in All files. Administration rows render only for admin accounts. Tokens unchanged from the Files UI: #0082C9 / #006AA3, 22 px pills, sidebar gradient, 12–13 px type. Implementation: same web frontend, routes /settings/<section>; each card maps to a server API call (profile, password rewrap, sessions, quota, devices, users; Backups → GET/POST /admin/backups + POST /admin/backups/{id}/verify). The S3 setup form and the schedule select need one new endpoint — PUT /admin/backups/config (test-then-save the connection, change the schedule or switch backups off; applied to the running server without restart); SYNCBOX_BACKUP_* env remains the fallback. Restore stays CLI.
